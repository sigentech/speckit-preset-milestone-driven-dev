## 目的

移植自 brainstorming 技能：你很擅长建造，但"你以为用户想要的"往往比你感觉的更薄。本命令用于在任何东西被建造之前，搞清楚用户到底想要什么、为什么——理解了"为什么"，那一百个用户没明说的决策你才会按他们的方式做。

**流程定位**：旁路技能，可在流程**任何环节**调用；不替代主线命令，头脑风暴的产出（设计文档 + 共识结论）沉淀到当前环节的正式产物，随后路由回主线继续。

## 用户输入

~~~text
$ARGUMENTS
~~~

用户想探讨的主题；缺省时先判定当前环节（见"结论沉淀"表），就当前环节最不确定的部分发起对话。

## 先想清楚：你到底知道什么？

回复之前自问：关于用户想要什么、为什么，我知道多少？

- **要点全在请求里**（"把图标改成矢车菊蓝"）：这是个清晰的小任务，直接做，说完即可——不必启动本流程。
- **有非平凡的部分缺失**：开始对话。

在进入实施之前，必须按序完成：

1. 把候选做法摊在一条独立消息里，让用户选一个（见"摆出做法"）
2. 写设计文档，简版或完整版（见"估量工作量"）
3. 获得用户对文档的批准
4. 按当前环节路由到对应主线命令继续（见"批准之后"）

两件事不算实施：用户同意做的探针（见"用探针摸情况"），以及用户明确选择跳过提问后直接按其要求执行。

## 先查证，再发问

在已有项目中、或用户给了上下文（一份 spec、一个计划、一次交接、指向的文件、此前的对话）时，发第一条消息前先深挖。读完用户指到的东西及其关联的代码或材料，直到你能讲清相关部分今天如何运作、本次改动会碰到什么。永远不问项目或上下文已经回答了的问题。

## 第一条消息

以下二选一，推动工作前进：

- **用户已说清要什么**（有 spec/计划/详细需求）：整条消息约 200 字。用你自己的话复述其需求——要什么、给谁、为什么，以他们已说出的为限。补上你查到的相关事实：相关部分今天如何运作、改动会碰到什么。若发现了他们可能没考虑过、会改变需求或建造方式的东西（约束、冲突、更便宜的路径），直说。怎么建造留到后面。结尾一行邀请纠正，再加一个关于"要什么"的问题：他们的请求里最开放、答案最能改变产物的那个点。spec 常常不完整，建立在它之上之前先确认。
- **用户没说清**：用他们自己的词汇问一个开放问题，关于请求里最大的未定项。说明为什么问：答案会改变你建什么。例如"面包店网站"："如果主要给路人决定是否进店，我会把营业时间和今日橱窗放最前；接订单则是另一种网站。你希望访客落地后做什么？"

消息如何收尾，取决于用户是否点名要头脑风暴：

- **点名要了**（提到本命令、或要求设计讨论）：以问题收尾。
- **没点名**：在问题后轻轻附一行"或者你想让我直接开干也行"。对方接受则本流程结束：用一句话说清重要的建造选择（平台、语言、载体），然后按正常流程执行。

整条消息就这么多。

## 对话

每条消息以**一个问题**收尾：一句话，后面不挂候选答案列表。用平实语言，略高于用户当前水平；贴用户的词汇；不用流程黑话；不需要向用户引用本命令。

清晰、简洁、要点先行。汇报发现时给最重要的，其余的提供备查。

**让用户描述。** 开放问题优先——用户自己的话带着选项装不下的意图。只在用户卡住时给短菜单。用户说"你看着办/你觉得呢"时，给出具体提案。

**怎么造。** 每个项目都依托于载体、工具、材料、资源的选择：应用的平台、语言、库。尽早弄清哪些选择用户想自己做、哪些交给你、手头已有什么。有主见有能力的用户会想聊透；指望着你的用户需要你用大白话给合理默认。有既有工作时沿用其技术栈。任何你做的选择，在设计文档里标为"我方决定"，绝不写成"双方商定"。

**要覆盖的地带**（是疆域，不是剧本，绝不照念）：这是哪类东西、特别之处在哪；为什么是现在、成功长什么样；目标/非目标/反目标（即使技术上成了，什么也算失败）；前作参照——见过什么、爱过恨过什么；现状——已有什么、试过什么；用户在意的细节。

**每个问题都要具体**：建立在用户上一个回答或你查到的东西上，帮他推演一个后果或遗漏的情形（"投票在会前截止，而本月有两名新成员。中途加入的人有投票权吗？"）。理由不言自明之外，说明你想学到什么、答案会改变什么。一个可被纠正的提案加你的理由，常常胜过一个提问。

**主动提供侦察。** 有了初步 grounding 且继续查有帮助时，提出去看看：更深的代码库、用户自己的文件数据、或网络。说明你要找什么。去不去由用户定。

**摆出做法。** 理解了要什么之后、写任何东西之前，把建造方式摊在一条独立消息里。想出若干个真实备选，扔掉弱的（包括与"为什么想要"相悖的、被既有工作排除的）。呈现剩下的两三个，各自落到项目实际上说它换了什么代价。推荐一个并说为什么，然后问用户选哪条。确实只有一条合理路径时，直说并解释其他为何不成立。这是"怎么造"的环节；"要什么"靠先让用户描述。

**用展示代替讲述。** 看见比读懂更有效时，提供可视化伴侣（见下）：用户要看的界面/页面/打印物/标识；屏幕、房间、日程的布局排布；流程或步骤序列；看起来不同的选项；看图比读字容易的结构（示意图、时间线、地图）。用户接受后，用它做可反应的稿图、并排选项、可点击的抛弃式原型。

**用探针摸情况。** 代理式工作是瀑布，但瀑布得非常快。一个快速的抛弃式构建常是搞清楚"想要什么/行不行"的最便宜方式。有帮助就提议。用户只想探针时别挡路。探针不写或只写最少测试、不追求坚固、跳过计划/实现/评审流程。把探针学到的东西带回对话。

## 回放

边聊边回放。一旦某部分理解得够清楚（它是干什么的、服务谁、某块如何行为），用约 200~300 字把这部分描述回去，再回到下一部分的问题。回放与提问贯穿全程交替，最后一段覆盖剩余部分。

只有用户说过的才记为"用户的"；你补的一切记为"我方提案"并附理由。每段结尾问：哪里不对、缺了什么。

发出一段回放前自查：它描述的是不是用户要看的东西（页面、屏幕、日程、打印物）？是，且可视化伴侣还没提供过——先发提供（独立消息），这段回放压到下一条。用户接受后，把稿图放在描述旁边。

## 估量工作量

理解了要什么、用户也选了做法之后，用大白话说清工作量，用户可推翻：

| 规模 | 设计文档 |
| --- | --- |
| 小改动 | 简版：把已聊清的内容落成文字 |
| 一个项目 | 完整设计文档（见下） |

简版或完整版，都必须含 **Approaches（做法）** 部分：考虑过的两三个做法、各自代价、用户选了哪个、为什么。选择在对话中完成，先于写文档。

做到一半发现变大了：停下，说明，升一档规模。如果这其实是多个独立项目：说明，商定顺序，一次只头脑风暴一个。

## 设计文档

写一份平实的文档：本领域有才华的建造者拿着它就能做计划，不必再回来问用户。覆盖：意图与为什么；目标/非目标/反目标；约束；做法（上述）；用户拍板的"怎么造"部分，按他们拍板的方式写；留给建造者的部分。

小改动的简版设计把同样要点各写一两行，直接给用户，不做建造者检查。

**文档落点（必须与调用时所在环节吻合，见"结论沉淀"表）**：

- 当前 spec 已存在 → `specs/NNN-mX-短名/design/YYYY-MM-DD-<主题>-design.md`，随 docs 提交
- 尚无当前 spec（项目级探讨：宪法/PRD/里程碑规划之前或之中）→ `docs/explore/YYYY-MM-DD-<主题>-design.md`，frontmatter 置 `status: pending-absorb`（头部格式从 `explore-note-template` 生成，用 `specify preset resolve explore-note-template` 定位）。该目录是下游命令的**自动吸收源**：`speckit.prd`、`speckit.milestones init` 执行时会扫描其中待吸收文件作为愿景素材，吸收后回写状态——设计文档不会因换环节而失联
- 用户另有偏好从其偏好

**建造者检查**（完整版设计文档）：文档写好后，派一个全新的通用子代理，提示词见模板——用 `specify preset resolve brainstorm-builder-check-prompt` 定位（通常为 `.specify/presets/milestone-driven-dev/templates/brainstorming/builder-check-prompt.md`），填入领域与文档路径。告诉用户"写好了，但会有一位评审先读，我可能带着几个问题回来一次"。检查回来之前不交文档。把评审的问题分三堆：

- **已回答**：对话或项目里已有答案 → 写进文档
- **次要**：合理的建造者不影响产物即可自行定夺 → 自己定，文档里标"我方决定"
- **只有用户能答**：答案会改变建什么 → 一条消息带回来，最重要的在前

用回答更新文档，交付时附一小段"我方决定"清单供用户审阅。这是检查产生的唯一一轮提问。宿主无子代理能力时，自己以建造者视角重读文档完成检查。

<HARD-GATE>
用户批准设计文档之前，什么都不建：不写产品代码、不搭脚手架、不装依赖、不建项目、不调用实施类技能。读和探查不受限。

两个例外：用户明确选择跳过提问，本流程与门禁一并结束；用户同意过的探针可以建，但始终标注抛弃式，想保留探针产出是新请求，要重新过这个门。
</HARD-GATE>

## 批准之后：路由回主线

设计文档获批后，按**调用时所在环节**路由到对应主线命令继续，而不是自由发挥：

| 调用时环节 | 批准后的下一步 |
| --- | --- |
| 未立宪法 | `/speckit.constitution`（结论作为宪法输入） |
| 无 milestones.md | `/speckit.prd`（愿景缺失）或 `/speckit.milestones init` |
| 里程碑已定、Demo 未冻结 | `/speckit.prototype gen Mx`（或继续 Demo 迭代） |
| Demo 已冻结、无 spec.md | `/speckit.specify` |
| spec 阶段有歧义 | `/speckit.clarify` |
| plan/tasks 阶段 | `/speckit.plan` / `/speckit.tasks` |
| 分析报告有待消除问题 | `/speckit.rectify` |
| 报告清零待实现 | `/speckit.implement` |

## 结论沉淀：与调用环节吻合

除设计文档外，对话中敲定的结论按当前环节写入正式产物（与 `/speckit.grill` 同一套落点表）：

| 调用时环节（证据） | 结论落点 |
| --- | --- |
| 无 constitution.md | `docs/explore/` 登记（pending-absorb）；立宪法访谈时自动参考 |
| 无 milestones.md | `docs/explore/` 登记（pending-absorb）；`speckit.prd` / `speckit.milestones init` 自动吸收 |
| prototype 未冻结未 skip | 就地修订 Demo + `prototype.md` 迭代记录 |
| spec.md 阶段 | 经 `/speckit.clarify` 口径写入 spec.md |
| plan.md 阶段 | plan.md 技术决策小节 |
| tasks/analyze/rectify 阶段 | 按 rectify 路由落笔 spec/plan/tasks + 分析报告附注 |
| implement/acceptance 阶段 | 不直接改代码，经 clarify→plan→tasks 路由回流 |
| 里程碑已 done | milestones.md 变更日志；增强 → 新里程碑候选 |

## 红旗

| 想法 | 现实 |
| --- | --- |
| "给用户列个可能想要的菜单" | 选项会带偏。先让用户描述。 |
| "我来填合理默认" | 好。但要说出口——没说过的默认等于用户没机会否决。 |
| "问题答完了，写文档吧" | 先在独立消息里摆出做法。 |
| "我该先解释流程" | 问你的问题。流程自己会显现。 |
| "用户对想法说了'挺好'" | 批准只覆盖你展示过的。没写出的设计文档不算被批准。 |
| "探针跑通了，接着往上建" | 保留是新请求，重新过门禁。 |

## 可视化伴侣

一个用于展示稿图、示意图、原型的浏览器标签页。是工具不是模式：接受它不等于每个问题都去浏览器。

**即时提供。** 第一次出现上述时刻才提供，绝不提前；提供本身是独立消息、不含别的内容：

> "这个可能看图更直观。要我开个浏览器标签页放几版稿图吗？"

用户拒绝则留在文字，除非用户重提否则不再提供。

**逐问判断：这个答案看图比读字更好懂吗？** 稿图、布局、示意图、并排方案进浏览器；需求、范围、取舍、概念选择留在文字。关于 UI 的话题不自动等于可视化问题。

用户接受后，先用 `specify preset resolve brainstorm-visual-companion` 定位指南（通常为 `.specify/presets/milestone-driven-dev/templates/brainstorming/visual-companion.md`），读完再按其说明启动服务（启动脚本在其同级 `scripts/` 目录，与指南的相对位置和上游技能一致）。会话文件落项目根的 `.superpowers/brainstorm/`，提醒用户把 `.superpowers/` 加入 `.gitignore`。

## 约束

- 本命令自身不写代码；设计文档与结论沉淀是唯一落笔处
- 结论落点永远跟随调用时所在环节（上表），不另起游离文件
- 结论若推翻已冻结产物（冻结的 Demo、已发布的里程碑），必须先请用户显式确认解冻/变更并留痕
